# K6: the concept graph and graph search — gate

Measured 2026-10-05 with `scripts/bench_k6.py` on operonx-kb `k6-graph` (a74cb13), operonx
main `ea92566`, `intfloat/multilingual-e5-small` on CPU, default `GraphSpec()` (seeds 3, expand 5,
alpha 0.3, title weight 3, max_df 0.5% / 10). No model call anywhere. Raw numbers: `k6.json`.

## Verdict

**Graph search stays opt-in** (`CollectionSpec(graph=GraphSpec())`, `mode="graph"`). On multi-hop
questions it is a large, significant lift (+0.17 Recall@10 on both sets); on single-hop sets it
costs a significant 0.02-0.06 of Recall@5 (no significant change at Recall@10). The PLAN's rule
(lift on multi-hop *and* no loss on single-hop) is not met, so `hybrid` stays the default. The
right use is a collection or a query known to need hops — the next step is the router (track5
§9.8) sending relation questions to `graph`.

## Multi-hop (test split, 300 questions each; settings chosen on the 100-question dev split)

Recall@k is the share of a question's supporting paragraphs in the top k. Paired bootstrap.

| set | mode | R@2 | R@5 | R@10 | R@20 | MRR | p50 / p95 ms |
|---|---|---|---|---|---|---|---|
| 2WikiMultihopQA (2 844 paragraphs) | hybrid | 0.609 | 0.705 | 0.771 | 0.808 | 0.958 | 272 / 544 |
| | **graph** | 0.614 | **0.878** | **0.943** | 0.956 | 0.958 | 327 / 605 |
| | Δ [95% CI] | +0.005 [0.000, 0.012] | **+0.174 [0.146, 0.201]** | **+0.172 [0.144, 0.200]** | | −0.000 | |
| MuSiQue-Ans (5 735 paragraphs) | hybrid | 0.464 | 0.573 | 0.630 | 0.689 | 0.815 | 186 / 480 |
| | **graph** | 0.462 | **0.709** | **0.798** | 0.846 | 0.812 | 288 / 599 |
| | Δ [95% CI] | −0.002 [−0.005, 0.000] | **+0.137 [0.104, 0.171]** | **+0.168 [0.133, 0.199]** | | −0.003 [−0.007, −0.000] | |

The lift is at Recall@5/10, not @2: the seeds keep their place and what they link to follows.

## No harm? Single-hop (K2 sets, all cases)

| set | R@5 hybrid → graph | Δ R@5 [95% CI] | Δ R@10 [95% CI] | Δ MRR |
|---|---|---|---|---|
| `xquad_en` (397) | 0.992 → 0.992 | 0.000 | −0.003 [−0.016, 0.010] | −0.000 |
| `xquad_vi` (397) | 0.995 → 0.977 | **−0.018 [−0.037, −0.004]** | −0.003 [−0.015, 0.008] | −0.002 (sig.) |
| `corpus_vi` (120) | 0.983 → 0.925 | **−0.058 [−0.117, −0.014]** | −0.008 [−0.046, 0.023] | −0.008 (sig.) |

Up to `expand` (5) walked chunks go in front of the hybrid's 4th-10th hits; on a single-hop question
those are incidental links. **The cap is what keeps Recall@10:** without it (every chunk the walk
reached ahead of the seed's other hits) `xquad_vi` fell to R@10 0.977 from 0.998.

## How the settings were chosen (dev splits only)

Grid on the 100 dev questions of each multi-hop set, over hybrid's dumped top-50 (`scratchpad`
prototype, same extraction and walk):

- Extraction: names-only vs names + content bigrams: equal on 2Wiki (R@10 0.983 / 0.985), +0.02 on
  MuSiQue (0.765 / 0.785, noise at n=100) for 3.7× the vocabulary → names only. Before fixing two
  extraction bugs found by reading the misses (`and` joined two names; names ran across a
  parenthesis) the graph gained only +0.04 on 2Wiki dev; 77 of the 80 missed paragraphs shared a
  concept with a found one.
- Seeds 3 (5 seeds fill the top 5 with seeds: no R@5 gain), alpha 0.3-0.5 equal, max_df 0.2-2% equal,
  title weight 3 (vs 1: R@10 0.96 → 0.98), query words as seeds: no gain.
- Ordering: walk-first beat RRF of walk and hybrid at every k tried (RRF k=1..60, walk weight 1-2);
  expand 5 equals uncapped on both dev sets.

## Cost

| | |
|---|---|
| Concept extraction at ingest | 1.2-1.4 s per 1M corpus tokens (regex; best of 5 over every chunk of the K2 sets) — invisible beside embedding |
| Graph size | 2Wiki 2 955 chunks / 21 480 concepts / 29 025 edges; MuSiQue 5 741 / 38 736 / 55 971 |
| Cold build (first query after a change) | 209 ms (2Wiki), 418 ms (MuSiQue); then cached per collection generation |
| Query latency | +55 ms p50 on 2Wiki, +100 ms on MuSiQue (CPU, 3 benches sharing 24 cores) |
