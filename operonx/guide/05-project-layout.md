# 5. Project layout and conventions

A product built on operonx looks like this. The files below are a complete,
working project, and `operonx init` writes this layout (with a feature of
its own) for you.

```text
scorer/
├── operonx.toml          # where the application is; what the CLIs load
├── resources.yaml        # models, stores, tracing — by key, secrets as ${VAR}
├── .env                  # the secrets themselves; never committed
├── pyproject.toml        # operonx[extras] as a dependency; pytest's paths
├── AGENTS.md             # for coding assistants (CLAUDE.md holds `@AGENTS.md`)
├── .operonx/guide/       # this guide, copied by `operonx guide --sync`
├── app/
│   ├── __init__.py
│   └── main.py           # APP = Application(...): read this file first
├── src/
│   └── scoring/          # one folder per feature
│       ├── __init__.py
│       ├── graph.py      # @graph functions: wiring only
│       ├── ops.py        # @op functions: the logic
│       └── _text.py      # private helpers (leading underscore)
├── tests/
│   └── test_scoring.py
├── datasets/             # eval cases, one .jsonl per dataset
└── docs/brd/             # the requirements and their checklist (`--no-brd` skips it)
```

`docs/brd/requirements/requirements_traceability.md` is the checklist: one
row per requirement, with its status, the code that meets it and the test
that shows it. Update a row when a change meets or alters its requirement.
`operonx-project` builds the open rows as milestones. Each milestone's
cards and their status are written to `docs/brd/board/`, in git, by the
engine only; never edit it. The engine's runtime state is
`.operonx/project/`, outside git, and is rebuilt from the board on a fresh
clone. The studio's Board tab shows the checklist, before the first
milestone too. How to build with it, and how to work a card yourself
(`take`/`submit`), is operonx-project's guide: `project/01-project.md` in
`.operonx/guide/` when it is installed.

## The rules

- **`ops.py` holds the logic, `graph.py` only wires it.** A graph function
  creates ops, reads their outputs and draws `>>` edges. No computation,
  no I/O, no conditionals in Python: branch with `if_()`.
- **Imports go one way:** `app/` → `src/<feature>/graph.py` → `ops.py` →
  `_helpers.py`. Nothing in `src/` imports `app/`.
- **`app/main.py` is the map of the product:** every service and job,
  with the graph each runs.
- **Resources by key.** Ops reach models and stores through
  `resources.yaml` keys (`LLMOp.of(resource="assistant")`), never by
  building clients. Secrets are `${VAR}` there and live in `.env`.
- **Every `@graph` is defined at module level, never inside a function.**
  No factory that builds a graph in a nested `def` and returns it. A
  setting (`k`, a threshold) is a graph input; a different shape is
  another module-level graph or an `if_` branch, picked in `app/main.py`.
  Edges stay written out (`START >> a >> b >> END`).

  ```python norun
  # no: a graph generated by a function
  def build_search(k=8):
      @graph
      def search(query): ...

      return search


  # yes: one graph, the setting is an input
  @graph
  def search(query, k): ...
  ```

  A provider op's `resource=` can be a graph input too
  (`LLMOp.of(resource=model, ...)` in `@graph def chat(model, q)`): the
  model or store is picked per run, so one graph serves them all.

- **Name graphs and ops for what they do** through their variables
  (`score = score_call(...)`), one op per line. Pin with `name=` only a
  name that other code reads (state keys, trace filters, evals).
- **Branch with `if_(...).else_(...)`** in the `>>` chain, never a
  hand-built `BranchOp`.
- **One feature, one folder.** Share code between features through a
  plain module, not by importing another feature's graph.
- **Test the ops directly** (`score(call=...)()`), and the graphs by
  running them with `Operon`.

```toml file=operonx.toml
name = "scorer"
```

```python file=src/scoring/_text.py
def word_count(text: str) -> int:
```

```python file=src/scoring/ops.py
from operonx import op

from scoring._text import word_count


@op
def score(id: str, text: str) -> dict:
    words = word_count(text)
    return {"id": id, "words": words, "verdict": "engaged" if words >= 5 else "brief"}
```

```python file=src/scoring/graph.py
from operonx import END, START, graph

from scoring.ops import score


@graph
def score_flow(id, text):
    s = score(id=id, text=text)
    START >> s >> END
```


```python file=app/main.py
"""The scorer: one HTTP service and the batch job over the same graph.

POST /score:8017 ──► score_flow ──► {id, words, verdict}
operonx run score_calls ──► score_flow per line of calls.jsonl ──► out/scored.jsonl
"""

from operonx.app import Application, Service, env, http
from operonx.app.jobs import Job

from scoring.graph import score_flow

APP = Application(
    "scorer",
    services=[Service("score", http("POST", "/score", port=env("PORT", 8017)), graph=score_flow)],
    jobs=[
        Job(
            "score_calls",
            graph=score_flow,
            items="calls.jsonl",
            output="out/scored.jsonl",
            key="id",
        )
    ],
)
```

```json file=calls.jsonl
{"id": "c1", "text": "yes I can talk now"}
{"id": "c2", "text": "busy"}
```

```python file=tests/test_scoring.py
import asyncio

from operonx import Operon
from operonx.app.jobs import Job

from scoring.graph import score_flow
from scoring.ops import score


def test_score_counts_words():
    assert score(id="a", text="one two")()["words"] == 2


def test_the_flow_scores_every_call():
    run = asyncio.run(
        Job(
            "t",
            graph=score_flow,
            items=[{"id": "a", "text": "hi"}],
            key="id",
            record_dir="out/test-jobs",
        ).run()
    )
    assert run.status == "ok" and run.results == {"a": {"id": "a", "words": 1, "verdict": "brief"}}
```

`operonx lint` checks the conventions of this page and of the project's
`AGENTS.md` (no `print()`, no graph inside a function, no logic in a
graph's body, the edges written out, every secret in `.env.example`, ...);
`operonx lint --rules` lists them, and `operonx lint --build` also loads the
application and builds every graph with the network blocked.

## Growing it

- **A second feature** is a second folder under `src/` with its own
  `graph.py` and `ops.py`, and one more entry in `app/main.py`.
- **A model** is an `llm:` entry in `resources.yaml` and an
  `LLMOp.of(resource=...)` in the feature's `graph.py`; its key goes in `.env`.
  Its provider's limits go on the entry, for the whole process:
  `rate_limit: {concurrency: 8, per_minute: 500}` (or `per_second`) — every
  op and run calling that key waits its turn; a stream holds its slot until
  it ends.
  A rule about what may be sent to a resource, for every op that calls it,
  is a guard: `ResourceHub.guard("llm:", check)` in `app/main.py`, with
  `check(key, method, args, kwargs)` raising to refuse — the call is never
  made (an `LLMOp` reports the error, like a provider's).
- **What every response passes through** — security headers, a request id —
  is ASGI middleware: `Application(..., middleware=[SecurityHeaders])` (or
  `[project] middleware = ["app.http:SecurityHeaders"]`), outermost first,
  each called `entry(app=app)`. It wraps the whole listener: the services'
  routes, a mounted app, `/healthz`.
- **An eval** is a `datasets/<name>.jsonl` and an `Eval(...)` (a kind of
  job) in `app/main.py`; `operonx run <eval>` gates CI.
- **What a run opens and closes** (a call's per-call objects, its record) are
  ops of its graph: the first op opens, `END >> op` closes. Not hooks in `app/`.
- **While developing:** `operonx serve --reload` restarts on a change;
  `--host`/`--port` bind elsewhere than declared. Every listener answers
  `GET /healthz`. `operonx init --editable ../Operon` makes a project use an
  operonx checkout (the default when made inside one).
