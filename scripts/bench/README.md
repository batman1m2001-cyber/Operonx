# Operonx e2e bench — Python vs Rust runtime

Three scripts that share a single set of `graph.json` + `inputs.json`
files, so the Python and Rust engines are exercised on the exact same
graph topology.

```
scripts/bench/
├── generate.py        # 1. dump graph.json + inputs.json per pattern
├── main.py            # 2. Python bench — runs each pattern through Operon
├── Cargo.toml
├── src/main.rs        # 3. Rust bench — runs each pattern through operonx
└── data/              # (gitignored) generated by generate.py
    ├── linear_50.graph.json
    ├── linear_50.inputs.json
    └── …
```

## Run

```bash
# 1. Generate the JSON fixtures (idempotent; re-run after editing patterns).
uv run python scripts/bench/generate.py

# 2. Python bench.
uv run python scripts/bench/main.py
uv run python scripts/bench/main.py --runs 50 --warmup 3

# 3. Rust bench.
cd scripts/bench && cargo run --release
cd scripts/bench && cargo run --release -- --runs 50 --warmup 3
```

Default: 200 timed runs + 5 untimed warmups per pattern.

## What's benched

22 patterns covering scheduler overhead, CPU-bound work, fan-out /
fan-in, nesting, branching, and production-shaped pipelines.

| Pattern | Shape | What it stresses |
|---|---|---|
| `linear_{50,100,200,500}` | n-op chain of `bench_noop` | Per-op scheduler overhead |
| `fib_chain_{10,20}x500` | n-op chain of `bench_fib(fib_n=500)` | Scheduler + bounded CPU |
| `parallel_{5,10,20}` | n parallel `bench_noop` → `combine_all` | Fan-out / fan-in |
| `matrix_chain_{5x30,5x60,10x40,5x100}` | chain of `bench_matrix` (naive O(n³) mat-mul) | Pure interpreted compute — fair Python↔Rust |
| `cpu_contention_{3h_10l,5h_10l}_30m` | n_heavy `bench_matrix(30)` + n_light `bench_noop` in parallel | Mixed CPU contention under scheduler |
| `nested_{2,5,10}` | top-level chain of `mid_pipeline` (@graph nesting 3 levels deep, pure `bench_noop`) | Nested `@graph` dispatch — pure scheduler overhead |
| `branching_{5,10}` | n stages of `classify → if_() → 4 paths → merge` | `if_()` branch routing |
| `production_{3,5}` | n parallel `verify_case` (@graph w/ `if_()` + `bench_matrix(30)`) → `combine_all` → noop | Realistic mixed workload |

Why no hash-chain patterns: Python's `hashlib.sha256` is OpenSSL C and
the Rust `sha2` crate is pure Rust, so any hash-chain bench measures
the hash library — not the engine. `matrix_chain_*` covers the
CPU-chain case fairly (naive O(n³) mat-mul, no library shortcut on
either side). `cpu_contention_*` swapped from `bench_hash` to
`bench_matrix` for the same reason.

The Rust bench flags silent failures: patterns that build-error or
return empty results show as `DEGENERATE` / `ERROR` in the `status`
column. The current goal is **all rows `ok`** — and they are.

To add a pattern: define a `@graph` factory + `@op` body in
`generate.py`, register it in `PATTERNS`, mirror the `#[op(name = ...)]`
in `src/main.rs` and add the name to the `known` list. The Rust bench
discovers patterns by scanning `data/`, so any matching
`<name>.graph.json` + `<name>.inputs.json` pair gets picked up.

| **cpu_contention_3h_10l_30m** | 12.29 ms | 0.77 ms | **16.0×** |

| **production_3** | 12.24 ms | 1.19 ms | **10.3×** (see caveat) |
| **production_5** | 20.49 ms | 1.86 ms | **11.0×** (see caveat) |

**Headline:** Rust wins every pattern. **2–3×** on linear / fan-out,
**1.3–1.5×** on pure-noop nested @graph dispatch (now), **10–11×** on
production-shape, **16–20×** under mixed CPU contention, and
**18–39×** on pure-compute matrix work.

**Caveat on branching/production:** these patterns parse and run, but
the `if_()` dispatch in Rust is partial — `cases` deserialise fine
(the `candidates` field landed) and the scheduler runs every branch
target, then a soft-edge merge picks the answer. Output values match
Python by coincidence in this bench; a graph where different branches
produce different results would diverge. Real branch dispatch needs
the ref-transform evaluator to land in Rust first — see
`REFACTOR_post_v0.6.2.md` ("Rust `if_()` branch routing dispatch").

**Nested @graph dispatch — closed.** Previously Rust lost on pure-noop
nesting because each nested call went through full `run_json_async`
(per-call `tokio::spawn` + new `mpsc::channel(64)` + UUID gen +
`pump_loop` task + middleware). The fast-path now precomputes a child
`GraphScheduler` for every nested `OpType::Graph` at parent build time
and dispatches via `child.run_collect(inputs)` inline in the caller's
task — no `spawn`, no channel allocation, no UUID gen. Mirrors
Python's `child._scheduler.run(state, ctx)` shape. Result:
`nested_{2,5,10}` are 1.3–1.5× Rust faster on pure noops, and
`production_*` jumped from 7.8× to **10–11×** because every nested
`verify_case` now uses the fast path.

## Notes

- The graph spec is generated by `generate.py` via `graph.serialize()`
  and patched with `schema_version = "1.0"` (the Rust loader requires
  it). Python-only fields (`python_callable`,
  `resource_config*`, `fallback_configs`) are stripped.
- Op names line up by string: Python `@op def bench_noop(...)` ↔ Rust
  `#[op(name = "bench_noop")]`. The Rust binary registers all `#[op]`s
  via `inventory` and resolves func_names at engine-build time.
- The `data/` directory is gitignored — regenerate locally.
